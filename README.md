# CodeStyle

Стиль кода для embedded-проектов на C/C++ (микроконтроллеры, прошивки, драйверы, библиотеки).

Главная идея простая: **код не должен знать, на каком железе он работает.** Всё, что касается конкретного микроконтроллера, живёт в одном слое — `Board/` (плюс `main.c`, который всё связывает). Остальной код получает доступ к железу только через указатели на функции. Благодаря этому:

- библиотеки и модули переносятся на другой МК без правок;
- логику можно покрыть unit-тестами на компьютере, подменив «железные» функции заглушками;
- проект легко читать: всегда понятно, где бизнес-логика, а где работа с периферией.

Живые примеры:
- библиотека — [LED](https://github.com/krllplotnikov-libraries/LED);
- проект целиком — [Terminal](https://github.com/krllplotnikov/Terminal).

## 1. Как устроен проект

За основу берутся файлы, которые сгенерировала IDE (например, CubeMX). Поверх них добавляются четыре папки:

```
Project/
├── Board/          ← аппаратные функции через HAL, по файлу на устройство
├── Libraries/      ← независимые библиотеки (LED, Button, RC522…), git submodules
├── Modules/        ← модули: кусочки бизнес-логики, собранные из библиотек
├── Applications/   ← приложение: связывает модули в готовый продукт
└── main.c          ← создаёт объекты, связывает их дескрипторами и запускает
```

| Слой | Что делает | Знает о железе? |
|---|---|---|
| `Board/` | Реализует аппаратные функции (`setState`, `transmit`…) через HAL. Ни состояния, ни логики — только обёртки над периферией | **Да** |
| `Libraries/` | Решает одну узкую задачу (мигать светодиодом, читать кнопку). Подключается через **git submodules**, чтобы одна библиотека жила во многих проектах | Нет |
| `Modules/` | Реализует часть бизнес-логики (например, «зуммер пищит при событии») на основе библиотек | Нет |
| `Applications/` | Вся бизнес-логика продукта, объединяет модули | Нет |
| `main.c` | Создаёт объекты, заполняет дескрипторы функциями из `Board/` и запускает систему | **Да** (только инициализация) |

Чтобы перенести проект на другой МК или плату, достаточно заново сгенерировать файлы IDE и переписать `Board/`. Всё остальное не меняется.

### Объект и дескриптор

Каждая сущность (светодиод, кнопка, модуль) — это **структура-объект**. Чтобы объект заработал, ему при инициализации передают **дескриптор** — структуру с «внешними» данными и аппаратными функциями:

```c
LED_Descriptor_st ledDescriptor = {
	.setState = ledSetState,   // как включить/выключить светодиод
	.getTick  = HAL_GetTick,   // откуда брать время
};

LED_Init(&led, &ledDescriptor);
```

Все функции модуля первым параметром принимают указатель на свой объект: `LED_Run(&led)`. Поэтому одна библиотека спокойно обслуживает сколько угодно экземпляров.

Дескриптор есть у всех объектов: у библиотек, модулей и приложений. В нём три вида полей:
- **зависимости** — аппаратные функции (`setState`, `getTick`) или указатели на объекты нижнего уровня (`LED_st* buzzer`);
- **колбэки событий** — через них объект сообщает наверх, что что-то произошло;
- **`void* context`** — указатель на того, кто подписан на события. Объект его не трогает, только хранит.

В `Libraries/`, `Modules/` и `Applications/` **нет глобальных переменных**: всё состояние лежит внутри объекта.

## 2. Как называть вещи

Имя должно сразу говорить, *что это* и *откуда оно*. Поэтому почти везде есть префикс модуля, а у типов — суффикс.

| Что | Как | Пример |
|---|---|---|
| Файлы | `PascalCase`, аббревиатуры заглавными | `Button.h`, `LED.h` |
| Константы `#define` | `UPPER_SNAKE_CASE` с префиксом модуля | `LED_INDICATIONS_MAX_SIZE` |
| Перечисление | `Модуль_Имя` + суффикс `_et` | `LED_State_et` |
| Значения перечисления | `UPPER_SNAKE_CASE` с префиксом | `LED_STATE_OFF` |
| Структура | `Модуль_Имя` + суффикс `_st` | `LED_Descriptor_st` |
| Тип указателя на функцию | `Модуль_Имя`, без суффикса | `LED_GetTick` |
| Тип колбэка события | `Модуль_Событие` + `Callback` | `LED_IndicationIsOverCallback` |
| Публичная функция | `Модуль_Действие` | `LED_SetIndication` |
| Обработчик чужого события | `Модуль_On` + событие | `ModuleBuzzer_OnIndicationIsOver` |
| Функция для вызова из прерывания | обычное имя + `FromISR` | `Button_OnInterruptFromISR` |
| Тип результата | `Модуль_Result_et`, значения `МОДУЛЬ_RESULT_...` | `RC522_Result_et`, `RC522_RESULT_OK` |
| Приватная (`static`) функция | `camelCase`, без префикса | `getPlayerIdByCardUID` |
| Переменные и поля | `camelCase`, осмысленно | `indicationRepeatCounter` |
| Параметры функций | `camelCase` с `_` в начале | `_led`, `_repeatCount` |

Подчёркивание у параметров помогает внутри функции отличить «то, что пришло снаружи» от полей и локальных переменных.

```c
void LED_SetIndication(LED_st* _led, LED_Indications_et _indication, uint8_t _repeatCount);
```

**Модули и приложения:**
- модули получают префикс `Module`: папка `Modules/Buzzer/`, файлы `ModuleBuzzer.h/.c`, тип `ModuleBuzzer_st`, функции `ModuleBuzzer_SingleBeep(...)`;
- приложения называются по своему имени: `Applications/Terminal/Terminal.c`, `Terminal_st`, `Terminal_Run`.

**Функции без параметров — всегда с `(void)`.** В C пустые скобки `()` означают «аргументы неизвестны», и компилятор не проверит вызов:

```c
typedef uint32_t (*LED_GetTick)(void);
void Terminal_Reset(void);
```

## 3. Заголовочный файл (`.h`)

Все заголовки устроены одинаково — открываешь любой и сразу знаешь, где что искать. Порядок секций:

1. Include guard — `LED_H_`.
2. `#include` — все зависимости модуля.
3. `#define` — константы.
4. Предварительные объявления перечислений: `typedef enum LED_State LED_State_et;`
5. Предварительные объявления структур: `typedef struct LED LED_st;`
6. Типы указателей на функции.
7. Определения `enum`.
8. Определения `struct`.
9. Прототипы функций внутри `extern "C"` — чтобы библиотеку можно было подключить из C++.

Зачем предварительные объявления? Чтобы все типы были известны компилятору заранее. Например, тип колбэка может принимать `LED_st*`, хотя сама структура описана ниже.

<details>
<summary>Пример заголовка целиком</summary>

```c
#ifndef LED_H_
#define LED_H_

#include <stdio.h>
#include <stdint.h>

#define LED_INDICATIONS_MAX_SIZE       16
#define LED_INDICATION_INFINITE_REPEAT 255

typedef enum LED_Indications LED_Indications_et;
typedef enum LED_State       LED_State_et;

typedef struct LED_Indication    LED_Indication_st;
typedef struct LED_Descriptor    LED_Descriptor_st;
typedef struct LED               LED_st;

typedef void     (*LED_IndicationIsOverCallback) (LED_st* _led, LED_Indications_et _indication, uint8_t _repeatCounter);
typedef uint32_t (*LED_GetTick)                  (void);
typedef void     (*LED_SetState)                 (LED_st* _led, LED_State_et _state);

enum LED_Indications{
	LED_INDICATION_OFF,
	LED_INDICATION_ON,
	LED_INDICATION_SINGLE_BLINK,
	LED_INDICATION_DOUBLE_BLINK,
	LED_INDICATION_TRIPLE_BLINK,
	LED_INDICATION_CUSTOM
};

enum LED_State{
	LED_STATE_OFF,
	LED_STATE_ON
};

struct LED_Indication{
	uint8_t  states[LED_INDICATIONS_MAX_SIZE];
	uint32_t durations[LED_INDICATIONS_MAX_SIZE];
	uint8_t  size;
};

struct LED_Descriptor{
	LED_SetState                 setState;
	LED_GetTick                  getTick;
	LED_IndicationIsOverCallback indicationIsOverCallback;
	void*                        context;
};

struct LED{
	LED_Descriptor_st  descriptor;
	LED_Indications_et currentIndication;
	LED_Indication_st* customIndication;
	uint8_t            indicationRepeatCount;
	uint8_t            indicationRepeatCounter;
	uint8_t            indicationDescriptorCounter;
	uint32_t           currentTime;
};

#ifdef __cplusplus
extern "C" {
#endif

void LED_Init(LED_st* _led, LED_Descriptor_st* _descriptor);
void LED_Run(LED_st* _led);

#ifdef __cplusplus
}
#endif

#endif
```

</details>

## 4. Файл реализации (`.c`)

Порядок секций (лишние просто пропускаются):

1. `#include` **только своего** заголовка — остальные зависимости уже подключены в `.h`.
2. Данные модуля — константные таблицы, готовые наборы.
3. Прототипы `static` функций.
4. Публичные функции — в том же порядке, что в `.h`; первыми `_Init` и `_Run`.
5. Обработчики событий нижнего уровня `[Модуль]_On[Событие]`.
6. Тела `static` функций — в самом конце.

### Жизненный цикл объекта

- **`_Init(obj, descriptor)`** — копирует дескриптор в объект и явно задаёт **все** остальные поля. Никаких «и так будет ноль».
- **`_Run(obj)`** — вызывается постоянно из главного цикла или задачи RTOS. Она **никогда не блокирует**: никаких `HAL_Delay` и ожиданий. Время берётся из `getTick()`. `_Run` верхнего уровня вызывает `_Run` своих зависимостей.
- Необязательные колбэки перед вызовом проверяются на `NULL`.

### Время и переполнение тиков

Счётчик `getTick()` типа `uint32_t` в миллисекундах переполняется примерно через **49,7 суток** и снова начинает с нуля. Если время сравнивается неправильно, устройство, проработавшее полтора месяца, «зависает»: таймеры либо срабатывают сразу, либо не срабатывают никогда. На столе такой баг не поймать.

**Правильно — запоминать момент начала и сравнивать прошедшее время:**

```c
if((currentTime - _led->startTime) >= _led->duration){
	...
}
```

При вычитании беззнаковых чисел переполнение «сокращается»: `0x00000010 - 0xFFFFFFF0` даёт `0x20`, то есть ровно 32 мс, которые прошли на самом деле.

**Неправильно — вычислять момент окончания:**

```c
uint32_t deadline = startTime + duration;   // может переполниться

if(currentTime >= deadline){                // сработает сразу или никогда
	...
}
```

Правила:
- в объекте хранится **время начала** (`startTime`), а не время окончания;
- сравнение всегда в виде `(currentTime - startTime) >= duration`;
- время, начало и длительность имеют **один и тот же беззнаковый тип**, по умолчанию `uint32_t`. Если тик уже, например `uint16_t`, разность нужно явно привести к нему: `(uint16_t)(currentTime - startTime)`. Иначе C расширит операнды до `int`, и разность станет отрицательной;
- текущее время читается из `getTick()` **один раз** в начале `_Run`, и дальше используется это значение. Тогда все проверки внутри одного прохода видят одинаковое время;
- в имени поля или константы указывается единица измерения, если она неочевидна: `timeoutMs`, `LED_BLINK_PERIOD_MS`;
- интервал не может быть больше периода переполнения. Длинные интервалы (часы, сутки) отсчитываются отдельным счётчиком: например, секунды увеличиваются раз в 1000 мс.

**В unit-тестах** заглушка `getTick` должна начинать отсчёт незадолго до переполнения, например с `0xFFFFFF00`. Так тесты проверят, что модуль корректно переходит через ноль.

### События: колбэки + context

Объект сообщает о событии, вызывая колбэк из своего дескриптора. Первым параметром колбэк всегда получает сам объект, поэтому обработчик знает, **кто** прислал событие. Через `descriptor.context` он получает **свой** объект, то есть того, кто подписался.

Так событие связано с конкретной парой экземпляров. Не нужны ни глобальные указатели, ни проверки вида `if(_x == instance->x)`, и каких угодно объектов может быть сколько угодно.

Пример: модуль зуммера сам подписан на событие LED и пробрасывает своё событие наверх.

```c
// ModuleBuzzer.h (фрагмент)
typedef void (*ModuleBuzzer_BeepIsOverCallback)(ModuleBuzzer_st* _moduleBuzzer);

struct ModuleBuzzer_Descriptor{
	LED_st*                         buzzer;
	ModuleBuzzer_BeepIsOverCallback beepIsOverCallback;
	void*                           context;
};

struct ModuleBuzzer{
	ModuleBuzzer_Descriptor_st descriptor;
};

void ModuleBuzzer_Init(ModuleBuzzer_st* _moduleBuzzer, ModuleBuzzer_Descriptor_st* _descriptor);
void ModuleBuzzer_Run(ModuleBuzzer_st* _moduleBuzzer);
void ModuleBuzzer_SingleBeep(ModuleBuzzer_st* _moduleBuzzer);
void ModuleBuzzer_OnIndicationIsOver(LED_st* _led, LED_Indications_et _indication, uint8_t _repeatCounter);
```

```c
// ModuleBuzzer.c
#include "ModuleBuzzer.h"

void ModuleBuzzer_Init(ModuleBuzzer_st* _moduleBuzzer, ModuleBuzzer_Descriptor_st* _descriptor){
	_moduleBuzzer->descriptor = *_descriptor;
}

void ModuleBuzzer_Run(ModuleBuzzer_st* _moduleBuzzer){
	LED_Run(_moduleBuzzer->descriptor.buzzer);
}

void ModuleBuzzer_SingleBeep(ModuleBuzzer_st* _moduleBuzzer){
	LED_SetIndication(_moduleBuzzer->descriptor.buzzer, LED_INDICATION_SINGLE_BLINK, 1);
}

void ModuleBuzzer_OnIndicationIsOver(LED_st* _led, LED_Indications_et _indication, uint8_t _repeatCounter){
	ModuleBuzzer_st* moduleBuzzer = (ModuleBuzzer_st*)_led->descriptor.context;

	if(moduleBuzzer->descriptor.beepIsOverCallback != NULL){
		moduleBuzzer->descriptor.beepIsOverCallback(moduleBuzzer);
	}
}
```

Приложение обрабатывает событие так же:

```c
void Terminal_OnBeepIsOver(ModuleBuzzer_st* _moduleBuzzer){
	Terminal_st* terminal = (Terminal_st*)_moduleBuzzer->descriptor.context;

	terminal->state = TERMINAL_STATE_IDLE;
}
```

Правила:
- обработчик чужого события — **публичная** функция `[Модуль]_On[Событие]` с точной сигнатурой колбэка. Она объявляется в `.h`, чтобы её можно было указать в дескрипторе;
- на одно событие — один подписчик. Если событие нужно нескольким, его раздаёт дальше обработчик в приложении;
- **weak-функции для событий не используются**: ошибку в имени линкер пропускает молча, переопределить можно лишь один раз на программу, а поведение зависит от компилятора.

### Ошибки

У каждой библиотеки и каждого модуля, которые могут завершиться с ошибкой, есть свой тип результата `[Модуль]_Result_et`. Первым значением всегда идёт `_OK`, оно равно нулю:

```c
enum RC522_Result{
	RC522_RESULT_OK,
	RC522_RESULT_BUSY,
	RC522_RESULT_ERROR_INVALID_ARGUMENT,
	RC522_RESULT_ERROR_BUS,
	RC522_RESULT_ERROR_TIMEOUT,
	RC522_RESULT_ERROR_CRC
};
```

Ошибки сообщаются по двум каналам, в зависимости от того, когда они обнаружены.

**1. Сразу — через возвращаемое значение.** Функция возвращает результат, если может отказать в момент вызова: неверный аргумент, объект занят, аппаратная функция вернула ошибку. Данные в этом случае возвращаются через указатели-параметры, которые идут последними.

```c
RC522_Result_et RC522_StartReading(RC522_st* _rc522);
RC522_Result_et RC522_GetUID(RC522_st* _rc522, uint8_t* _uid, uint8_t* _size);
```

**2. Позже — через колбэк ошибки.** Так как `_Run` не блокирует, многие ошибки выясняются не в момент вызова, а через несколько проходов цикла: датчик не ответил за отведённое время, не сошлась контрольная сумма. Такие ошибки объект передаёт колбэком из дескриптора:

```c
typedef void (*RC522_ErrorCallback)(RC522_st* _rc522, RC522_Result_et _result);
```

Правила:
- **Функции, которые не могут отказать, остаются `void`.** `LED_SetIndication` не нужно возвращать `_OK` ради единообразия.
- **Результат всегда проверяется.** Если его сознательно игнорируют, это пишется явно: `(void)RC522_StartReading(&rc522);`.
- **Аппаратные функции, которые могут отказать, возвращают тип результата своей библиотеки.** `Board/` переводит в него код HAL, а `HAL_StatusTypeDef` дальше `Board/` не уходит:

  ```c
  RC522_Result_et BoardRC522_Transmit(RC522_st* _rc522, uint8_t* _data, uint16_t _size){
  	if(HAL_SPI_Transmit(&hspi1, _data, _size, BOARDRC522_SPI_TIMEOUT) != HAL_OK){
  		return RC522_RESULT_ERROR_BUS;
  	}

  	return RC522_RESULT_OK;
  }
  ```

- **Каждый слой возвращает свой тип.** Модуль не пробрасывает `RC522_Result_et` наверх, а переводит его в `ModuleRFID_Result_et`. Тогда приложение не зависит от того, какой чип стоит внутри модуля.
- **Аргументы, пришедшие снаружи (индекс, размер, номер канала), проверяются**, и при ошибке возвращается `_ERROR_INVALID_ARGUMENT`. Указатель на свой объект не проверяется: передать `NULL` вместо объекта — ошибка программиста, а не ситуация во время работы.
- **Библиотеки и модули не решают, что делать с ошибкой**: не уходят в бесконечный цикл, не вызывают `Error_Handler()`, не перезагружают МК. Они только сообщают об ошибке. Повторить, показать пользователю или сбросить устройство решает приложение.

## 5. Работа с железом: `Board/` и `main.c`

### Board/

Здесь лежат все функции, которые обращаются к HAL. Если оставить их в `main.c`, на проекте с десятком устройств он вырастет до тысяч строк. Поэтому у каждого физического устройства своя пара файлов:

```
Board/
├── Board.h              ← подключает все Board*.h, его включает main.c
├── Board.c              ← общие функции платы (критические секции и т.п.)
├── BoardBuzzer.h / .c
├── BoardRC522.h / .c
└── BoardDisplay.h / .c
```

Правила:
- имена: файлы `Board[Устройство]`, функции `Board[Устройство]_[Действие]`, например `BoardBuzzer_SetState`;
- сигнатура функции **точно совпадает** с типом указателя из библиотеки, чтобы её можно было прямо положить в дескриптор;
- **одна функция — одно устройство.** Если светодиодов два, будут `BoardLedRed_SetState` и `BoardLedGreen_SetState`, а не одна функция с проверкой `if(_led == &ledRed)`. Тогда `Board/` не нужно знать об объектах из `main.c`;
- никакого состояния и бизнес-логики — только вызов HAL;
- `Board/` знает о библиотеках (берёт из них типы), библиотеки о `Board/` не знают;
- хэндлы периферии (`huart1`, `hspi1`) берутся из сгенерированных заголовков. В CubeMX для этого включается опция *Generate peripheral initialization as a pair of .c/.h files per peripheral*, после чего подключается `usart.h`, `spi.h` и т.д. Без неё хэндлы объявляются через `extern` в `.c` устройства;
- файлы оформляются по тем же правилам, что и любые `.h` / `.c` (разделы 3 и 4).

```c
// BoardBuzzer.h
#ifndef BOARDBUZZER_H_
#define BOARDBUZZER_H_

#include "main.h"
#include "LED.h"

#ifdef __cplusplus
extern "C" {
#endif

void BoardBuzzer_SetState(LED_st* _led, LED_State_et _state);

#ifdef __cplusplus
}
#endif

#endif
```

```c
// BoardBuzzer.c
#include "BoardBuzzer.h"

void BoardBuzzer_SetState(LED_st* _led, LED_State_et _state){
	HAL_GPIO_WritePin(BUZZER_GPIO_Port, BUZZER_Pin, (_state == LED_STATE_ON) ? GPIO_PIN_SET : GPIO_PIN_RESET);
}
```

### main.c

`main.c` теперь только собирает систему: создаёт объекты, связывает их и запускает. Аппаратных функций в нём нет.

Если `main.c` сгенерирован IDE, свой код пишется **только** внутри блоков `/* USER CODE BEGIN … */ … /* USER CODE END … */`, чтобы перегенерация ничего не стёрла. В `USER CODE BEGIN Includes` подключается `Board.h` и заголовок приложения.

В `USER CODE BEGIN 0` код разбит на секции с маркерами `//-----Имя-----` (между секциями — три пустые строки, внутри — подсекции по устройствам вроде `//-----Buzzer-----`):

| Секция | Что внутри |
|---|---|
| `//-----Variables-----` | Все объекты `= {0}`, выровнены по колонкам. Сначала библиотеки, потом модули, потом приложение |
| `//-----Descriptors-----` | Дескрипторы через designated initializers: функции из `Board/` и связи событий (колбэк + `context`) |
| `//-----Callbacks-----` | Только колбэки вендора (`HAL_GPIO_EXTI_Callback` и т.п.), которые передают аппаратные события в библиотеки. Им нужны объекты из `main.c`, поэтому они живут здесь. **Бизнес-логики здесь нет** |

Так в `main.c` видна вся схема связей проекта: кто кому что передаёт.

```c
//-----Descriptors-----
LED_Descriptor_st buzzerDescriptor = {
	.setState                 = BoardBuzzer_SetState,
	.getTick                  = HAL_GetTick,
	.indicationIsOverCallback = ModuleBuzzer_OnIndicationIsOver,
	.context                  = &moduleBuzzer,
};

ModuleBuzzer_Descriptor_st moduleBuzzerDescriptor = {
	.buzzer             = &buzzer,
	.beepIsOverCallback = Terminal_OnBeepIsOver,
	.context            = &terminal,
};
//-----Descriptors-----
```

В `main()`:
1. после инициализации периферии вызываются `_Init` снизу вверх: библиотеки → модули → приложение;
2. в бесконечном цикле (или задаче RTOS) вызывается только `_Run` приложения: `Terminal_Run(&terminal);`.

## 6. Прерывания и общие данные

Прерывание может случиться посреди любой строки `_Run`. Если оба меняют одни и те же данные, получается гонка: баг, который появляется раз в неделю и не воспроизводится в отладчике. Поэтому правило одно: **в прерывании только фиксируем факт, обрабатываем в `_Run`.**

### Что можно в прерывании

- Колбэк вендора в `main.c` вызывает функцию библиотеки с суффиксом `FromISR`, например `Button_OnInterruptFromISR(&button)`. Других вызовов из прерывания нет.
- Функция `...FromISR` только увеличивает счётчик, кладёт байт в кольцевой буфер или запоминает время. Обычно это одна-две строки.
- **Колбэки событий из прерывания не вызываются никогда.** Объект сообщает о событии наверх только из своего `_Run`. Благодаря этому вся логика модулей и приложения выполняется в основном потоке, и думать о гонках там не нужно.
- В прерывании нельзя ждать, писать циклы опроса, вызывать `HAL_Delay`, `printf` и тяжёлые функции HAL.

### Как передавать данные из прерывания

**Один писатель на переменную.** Каждую общую переменную меняет только одна сторона: либо прерывание, либо `_Run`. Тогда критическая секция не нужна. Для этого есть два стандартных приёма.

**Счётчик событий вместо флага.** Флаг, который прерывание ставит, а `_Run` сбрасывает, теряет событие, если оно повторится между чтением и сбросом. Со счётчиком такого не бывает: прерывание его увеличивает, а `_Run` сравнивает со своей копией.

```c
struct Button{
	Button_Descriptor_st descriptor;
	volatile uint32_t    interruptCounter;   // пишет только прерывание
	uint32_t             processedCounter;   // пишет только _Run
};

void Button_OnInterruptFromISR(Button_st* _button){
	_button->interruptCounter++;
}

void Button_Run(Button_st* _button){
	if(_button->interruptCounter != _button->processedCounter){
		_button->processedCounter = _button->interruptCounter;

		if(_button->descriptor.pressedCallback != NULL){
			_button->descriptor.pressedCallback(_button);
		}
	}
}
```

```c
// main.c
//-----Callbacks-----
void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin){
	if(GPIO_Pin == BUTTON_Pin){
		Button_OnInterruptFromISR(&button);
	}
}
//-----Callbacks-----
```

**Кольцевой буфер для потока данных** (UART, АЦП). Индекс `head` двигает только прерывание, индекс `tail` — только `_Run`. Блокировки не нужны.

### Правила для общих полей

- Поле, которое меняет прерывание, объявляется `volatile`. Иначе компилятор может закэшировать значение, и `_Run` его не увидит.
- `volatile` **не делает операцию атомарной**. Общее поле должно быть не шире разрядности МК: на 32-битном Cortex-M подходит `uint32_t`, на 8-битном AVR — только `uint8_t`.
- Если данные нельзя разделить по правилу «один писатель» (структура из нескольких полей, которые меняются вместе), используется критическая секция. Это тоже работа с железом, поэтому она приходит через дескриптор: поля `enterCritical` / `exitCritical`, реализации `Board_EnterCritical` / `Board_ExitCritical` лежат в `Board.c`. Реализация должна корректно работать при вложенных вызовах (сохранять и восстанавливать `PRIMASK`, а не просто вызывать `__enable_irq()`). Внутри критической секции — только копирование данных, ничего больше.

### RTOS

Каждый объект принадлежит одной задаче: его `_Run` и все его функции вызываются только из неё. Данные между задачами передаются через средства RTOS (очереди, уведомления). Функции RTOS тоже приходят через дескриптор и реализуются в `Board/`.

## 7. Форматирование

- Отступы — табуляция.
- Фигурная скобка — на той же строке, без пробела: `struct LED{`, `void LED_Run(LED_st* _led){`.
- Звёздочка указателя — у типа: `LED_st* _led`.
- После `if`, `for`, `while`, `switch` пробела нет: `if(...)`.
- `else` — с новой строки после `}`:

  ```c
  if(state == LED_STATE_ON){
  	...
  }
  else{
  	...
  }
  ```

- В `switch` метки `case` на уровне `switch`, тело каждого `case` в фигурных скобках, `break;` внутри, в конце `default: break;`:

  ```c
  switch(terminal->state){
  case TERMINAL_STATE_START:{
  	...
  	break;
  }

  default: break;
  }
  ```

- Однотипные строки (`#define`, объявления типов, поля структур) выравниваются по колонкам.
- Смена состояния (`terminal->state = ...;`) — последней строкой блока, отделена пустой строкой.
- Секции отмечаются парными комментариями `//-----Имя-----` в начале и в конце.

## 8. Чек-лист для ревью

- [ ] К HAL обращаются только `Board/` и `main.c`, остальное получает железо через дескриптор.
- [ ] В `Board/` по паре файлов на устройство, одна функция обслуживает одно устройство, нет состояния и логики.
- [ ] В `main.c` нет аппаратных функций — только объекты, дескрипторы, колбэки вендора, `_Init` и `_Run`.
- [ ] У каждого объекта есть структура и дескриптор; первый параметр функций — указатель на объект.
- [ ] Имена соответствуют правилам: `_et` / `_st`, префикс модуля, `_` у параметров.
- [ ] Секции `.h` в правильном порядке, типы объявлены заранее, прототипы в `extern "C"`.
- [ ] Внешние библиотеки — git submodules в `Libraries/`.
- [ ] Функции без параметров объявлены с `(void)`.
- [ ] Секции `.c` в правильном порядке, `static` функции в `camelCase` и в конце файла.
- [ ] `_Init` задаёт все поля, `_Run` не блокирует, необязательные колбэки проверяются на `NULL`.
- [ ] Время сравнивается только как `(currentTime - startTime) >= duration`, в одном беззнаковом типе; моменты окончания не вычисляются.
- [ ] `getTick()` читается один раз за проход `_Run`; тесты проверяют переход тика через ноль.
- [ ] События — только колбэки в дескрипторе с `void* context`; weak-функций и глобальных указателей на экземпляр нет.
- [ ] Обработчики чужих событий — публичные `[Модуль]_On[Событие]`, связи заданы в дескрипторах в `main.c`.
- [ ] В `main.c` код только в `USER CODE`, разбит на секции, в колбэках нет бизнес-логики.
- [ ] Из прерывания вызываются только функции `...FromISR`; они лишь фиксируют факт, колбэки событий из прерывания не вызываются.
- [ ] У каждой общей с прерыванием переменной один писатель; поле `volatile` и не шире разрядности МК.
- [ ] Критические секции приходят через дескриптор, корректны при вложенности и содержат только копирование данных.
- [ ] С RTOS каждый объект используется только из одной задачи.
- [ ] Функции, которые могут отказать, возвращают `[Модуль]_Result_et` (`_OK` = 0); остальные — `void`.
- [ ] Ошибки, обнаруженные в `_Run`, передаются колбэком ошибки из дескриптора.
- [ ] Результат всегда проверяется или явно игнорируется через `(void)`.
- [ ] Коды HAL не выходят за `Board/`, а каждый слой возвращает свой тип результата.
- [ ] Библиотеки и модули не обрабатывают ошибки сами (`Error_Handler`, бесконечный цикл, сброс) — решает приложение.
